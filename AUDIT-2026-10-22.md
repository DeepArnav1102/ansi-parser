# ansi-parser security and quality audit

**Audit date:** 2026-10-22  
**Scope:** Current working tree, including uncommitted changes. Reviewed the Rust library, tests, fuzz harnesses, manifest, public parsing/rendering/input APIs, and dependency graph. This was a source review and local verification, not a penetration test of an application that embeds the crate.

## Executive summary

The parser itself is memory-safe Rust and has useful bounded buffers for CSI parameters (256 bytes), OSC payloads (4 KiB), and DCS payloads (32 KiB). No `unsafe` code, embedded credentials, network client, filesystem write path, or production runtime dependency was found.

There are no critical findings, but there are two denial-of-service risks when callers pass untrusted input or dimensions, and multiple correctness defects in the higher-level streaming, screen, style, and diff APIs. The most urgent fixes are validating modified-key input before arithmetic and bounding/checked-multiplying screen dimensions.

## Findings

### High — unbounded screen dimensions can overflow or exhaust memory

**Affected code:** `src/screen.rs:75-84`; SVG rendering in `src/diff.rs:220-235`.

`TerminalGrid::new` accepts caller-provided `usize` dimensions, calculates `rows * cols` without `checked_mul`, then allocates that many cells. Values such as `usize::MAX, 2` panic in debug builds on overflow; large non-overflowing values can attempt a process-terminating allocation. The same unvalidated dimensions are used in multiplications for SVG width and height.

**Impact:** A caller that maps untrusted terminal/window-size metadata directly to `Screen::new` can be remotely crashed or forced into memory exhaustion.

**Recommendation:** Make construction fallible (`try_new`) or validate a documented maximum row count, column count, and cell count before allocation. Use `checked_mul` and return a typed error for overflow or over-limit dimensions. Apply checked arithmetic to exported snapshot/SVG size calculations as well.

### Medium — malformed modified-key sequence panics in debug builds

**Affected code:** `src/input.rs:474-495`, especially line 476.

`decode_input_sequence(b"\x1b[1;!A")` matches the modified-cursor-key prefix and evaluates `b'!' - b'0'`. This underflows `u8` and panics in debug/test builds. In release builds it wraps and can produce an incorrect modifier value instead of rejecting the sequence.

**Impact:** A malformed byte sequence from a terminal, PTY, test fixture, or untrusted transport can crash debug deployments. The parser is advertised as resilient to malformed input, so the inconsistent release behavior is also a correctness problem.

**Recommendation:** Validate `bytes[4].is_ascii_digit()` before subtracting, or use `checked_sub`. Validate that the complete modifier is in the accepted xterm range before emitting an event. Add this exact regression input and structured malformed-sequence cases to `tests/input_tests.rs` and the fuzz corpus.

### Medium — `Screen::feed` is not incremental despite accepting byte chunks

**Affected code:** `src/screen.rs:329-335`.

Each `Screen::feed` call creates a new `Parser`. Escape sequences split between calls are discarded or interpreted as printable text. For example, feeding `b"\x1b[31"` followed by `b"mX"` should render `X` red, but the second call starts in parser ground state and renders the suffix as text.

**Impact:** Consumers processing PTY/socket reads in chunks get a screen different from the original terminal stream. If the screen is used to sanitize or inspect terminal output, this can make control-sequence handling unreliable.

**Recommendation:** Store a `Parser` inside `Screen` and feed it across calls, or rename this method to document one-shot semantics and add a separate incremental API. Add split-boundary tests for CSI, OSC/ST, DCS, and UTF-8 text.

### Medium — `StyleTracker::feed_to_spans` loses parser state on every call

**Affected code:** `src/style.rs:223-242`.

The tracker preserves `current_style`, but creates a new `Parser` on every call. A split SGR/OSC sequence is therefore not parsed consistently. This is particularly surprising because the method is named `feed_to_spans` and is on a stateful tracker.

**Impact:** ANSI-to-HTML/style consumers can emit incorrect text or styles when input arrives in normal streaming chunks.

**Recommendation:** Put a `Parser` in `StyleTracker`, preserve it across `feed_to_spans` calls, and offer an explicit one-shot helper for callers that want a fresh parser. Test every split point around SGR sequences and multi-byte UTF-8 characters.

### Medium — ANSI diff generation cannot faithfully reproduce all supported styles

**Affected code:** `src/diff.rs:97-135` and `src/diff.rs:154-198`.

`Style` supports double underline, both blink modes, hidden, strikethrough, overline, and underline color, but `current_style_to_sgr` emits none of them. It also assumes the physical terminal begins with default SGR state (`current_style = Style::default()`), even though the supplied `from: &Screen` may have a different active rendition state. Consequently, `generate_ansi_diff` can claim to transform one screen into another while emitting output that renders with missing or stale styling.

**Impact:** Visual diffs are incorrect; if generated ANSI is sent to a user terminal, output may retain a prior style unexpectedly.

**Recommendation:** Start generated output with `CSI 0 m` before the first write, serialize every representable `Style` field (including `58;...`), and add round-trip tests that apply a patch to a non-default styled source screen. Document incompatible terminal capabilities where a style has no portable ANSI representation.

### Low — base64 clipboard decoder accepts malformed encodings

**Affected code:** `src/osc.rs:205-237`.

`decode_base64` stops at the first `=` and returns `Some` without validating padding placement, residual bits, or trailing non-whitespace data. Examples such as `b"A"`, `b"===="`, and `b"SGVsbG8=garbage"` are accepted, with the latter silently decoding only the prefix.

**Impact:** A consumer that treats `Some` as proof of a valid OSC 52 clipboard payload can accept truncated or ambiguous data.

**Recommendation:** Use a tested decoder or implement strict RFC 4648 validation: accepted alphabet, length modulo four, legal final padding, zero discarded bits, and no content after padding. Keep a decoded-size limit.

### Low — OSC actions expose dangerous terminal intents without a policy boundary

**Affected code:** `src/osc.rs:120-177`, `src/osc.rs:181-202`.

The API turns untrusted OSC data into `SetHyperlink`, `SetCurrentWorkingDirectory`, and `Clipboard` actions, including OSC 52 writes, without scheme, control-character, host, or clipboard-size validation. The crate does not itself open URLs or write a clipboard, so this is not a direct vulnerability in the crate. It becomes one if an embedding application applies these actions automatically.

**Recommendation:** Keep parsing separate from execution, document OSC 52 as opt-in only, and provide a policy/filter API with safe defaults. Consumers should reject control characters, enforce length limits, require an allowlist of URL schemes (normally `https`/`http`), and require explicit user consent before clipboard writes or external navigation.

### Low — documented feature matrix is broken without default features

**Affected code:** `Cargo.toml:11-14`, `src/lib.rs:1-24`, and modules that import `alloc` unconditionally.

The crate declares `alloc` and `std` features and uses `#![no_std]`, but `cargo test --no-default-features` fails with 94 compilation errors: public modules still compile while `alloc` imports, `vec!`, and `format!` are unavailable. There is no documented supported no-allocation configuration.

**Impact:** Downstream users cannot build the advertised feature shape without default features. This is primarily a release/compatibility issue, but it can lead to unsafe downstream forks or abandoned updates in embedded projects.

**Recommendation:** Either require `alloc` unconditionally and remove the misleading feature toggle, or gate allocation-dependent APIs/modules correctly and add `cargo check --no-default-features` to CI.

## Additional quality issues

1. Parser output is byte-oriented, but `Screen::process_event` converts each `Event::Print` independently with `String::from_utf8_lossy` (`src/screen.rs:344-349`). UTF-8 characters split between parser feeds become replacement characters. Preserve a UTF-8 carry buffer in the screen renderer or operate on bytes until a complete scalar is available.
2. `ScreenDiff::compute` compares only the overlapping rectangle when screen dimensions differ (`src/diff.rs:49-64`) yet exposes no incompatibility/error. A generated ANSI patch cannot resize a terminal, so reject different dimensions or state this as a strict precondition.
3. `AnsiReader` correctly retains parser state, but it exposes arbitrary `Event::Print` chunks at read boundaries (`src/stream.rs:30-38`). Consumers that stringify individual events must retain incomplete UTF-8 themselves. Document this contract or add a text-oriented reader that buffers incomplete UTF-8.
4. The public API lacks a parser finalization method. At EOF, incomplete escape sequences are silently dropped by `AnsiReader`; that may be intentional, but a `finish`/`into_remainder` API would let callers choose whether to retain or report them.
5. `feed_each` is documented as “zero-allocation” (`src/parser.rs:83-89`) but allocates a text `Vec` per call and allocates sequence buffers/events as needed. Update the documentation or redesign the callback API to borrow text where possible.

## Positive controls observed

- Parser accumulation limits and recovery states prevent unbounded CSI/OSC/DCS sequence growth.
- Raw 8-bit C1 controls are disabled by default, which avoids misclassifying UTF-8 continuation bytes.
- HTML output escapes `&`, `<`, `>`, quotes, and apostrophes before inserting print text.
- No `unsafe` blocks were found in the repository.
- The repository includes property tests and libFuzzer targets for parser, chunks, screen processing, stripping, and input decoding.

## Recommended remediation order

1. Fix modified-key parsing and add regression/fuzz inputs.
2. Make screen allocation and render-size arithmetic checked and bounded.
3. Preserve parser and UTF-8 state in `Screen` and `StyleTracker`.
4. Make ANSI diff output a faithful serialization of `Style`, beginning from a known terminal style state.
5. Add an explicit OSC execution-policy layer and strict base64 validation.
6. Decide and test the supported `no_std`/`alloc` feature matrix in CI.
